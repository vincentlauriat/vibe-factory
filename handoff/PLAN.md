# PLAN — 0.5 "see everything that was done"

Status: approved 2026-09-27 ("go, chain the steps without asking"), in progress on branch `feat/visibility-0.5`: one commit per step, one PR at the end. Step 7 (macOS app) added the same day at Vincent's request. Inventory of the current state: `.omc/research/visibility-inventory.md`.

Three user-facing capabilities, one foundation:

| | Capability | Surfaces |
|---|---|---|
| A | **History** of finished work: per task, the runs, commits, changed files, QA verdict, validations, tokens, active time | `vibe history`, web view *History*, TUI screen |
| B | **Global activity** feed across all tasks, live, filterable by type and task | `vibe events` without a task, web view *Activity*, TUI screen |
| C | **Full trace** of a run: every tool call with its complete arguments, exit code, duration and complete output | `vibe trace <REF>`, web tab *Trace*, TUI tab |
| D | **macOS app**: a native client of `vibe serve` with the board, approvals, history, activity and trace | `apps/macos/VibeFactory` (Step 7) |

Rule kept throughout (ADR-007): the run manager is the only seam, `.vibe/` is the source of truth, and every interface rebuilds its view from persisted events plus git. Nothing below adds a private cache that events could not reconstruct.

## Gaps that force engine changes first

From the inventory (file:line references there):

1. `ToolCalled`/`ToolReturned` have no call id and no `subtask`; returns of parallel tools cannot be paired reliably. `ToolReturned` carries a 200-char `preview` only; `ToolOutput.metadata` (exit code, timeout) is dropped; the full output is kept nowhere below 100 000 chars.
2. The final merge SHA lives only in `progress.md` and in a `PhaseFinished.summary` string. Checkpoint/fix commits emit no event. Only `SubtaskIntegrated` carries a hash.
3. `RunFinished` carries no usage or duration; `run.json` is overwritten by the next run, so per-run totals of earlier runs are lost. `Task` has no `branch`; every command recomputes the worktree location with default settings.
4. `AgentStarted` has no model name.
5. No API reads events across tasks; events other than `RunStarted` do not carry the task (it is implied by the file they sit in). `load_events` parses whole files; `--follow` and the server re-read everything every 250–300 ms.

All additions below are **optional fields or new event types**: schema stays 2 (documented as non-breaking in `events.md`). Old logs keep loading; the new views degrade (no exit code, order-based pairing) on runs recorded before this release.

## Step 1 — Events and persistence (crates vibe-core, vibe-agents, vibe-pipeline)

- `ToolCalled { …, call: CallId, subtask: Option<SubtaskId> }`, `ToolReturned { …, call, subtask, exit_code: Option<i64>, timed_out: bool, output_chars: u64, output_file: Option<String> }`. `CallId` = short uuid, generated by the runtime per call.
- Full tool outputs written to `<project>/.vibe/tool-output/<task dir>/<run>/<call>.txt` (the directory `.vibe/.gitignore` already ignores). The copy of oversized outputs the runtime leaves in `<workspace>/.vibe/tool-output/<uuid>.txt` for the model stays as it is: the agent only reads inside its workspace, so outputs above the model limit exist twice (decided at implementation, see `.omc/research/step1-report.md`). `pipeline.trace_outputs = true` (default) and `pipeline.trace_max_chars = 100_000` per call. `task discard` removes the task's trace directory.
- `AgentStarted { …, model: String }`.
- New event `Committed { run, subtask: Option, commit, message, files: Vec<String> }` published by `ctx.commit` (checkpoints, fix commits) and by subtask integration; new event `Merged { run, commit, branch, base }` from the merge phase. `SubtaskIntegrated` unchanged.
- `RunFinished { …, usage: Usage, active_ms: u64, started_at }` so every run's totals survive in `events.jsonl`.
- `Task.branch: Option<String>` persisted when the workspace is opened; `worktree_location`, `vibe pr`, `task show`, `task discard` prefer it.
- `docs/src/reference/events.md` updated; `TYPES`/`type_name` tests keep enforcing the doc.

Verification: unit tests on the runtime (call ids pair under parallel tools, output file written and referenced, cap respected), pipeline tests for `Committed`/`Merged`, event doc test, the existing suite.

## Step 2 — Read layer (crate vibe-pipeline, no UI)

- `EventReader`: incremental reading of one `events.jsonl` by byte offset (used by `--follow`, the server stream and the TUI instead of full re-parses).
- `Store::all_events(since)`: every task's log, each envelope tagged with `{task, number}`, ordered by `at`. A `TaggedEnvelope { task, number, envelope }` type for interfaces.
- `history::task_history(store, git, task) -> TaskHistory`: built from `task.json`, all runs in `events.jsonl` (`RunStarted`…`RunFinished`: status, started/finished, usage, active time, phases), commits (`Committed`, `SubtaskIntegrated`, `Merged`), changed files (`git diff --name-status <base>...<branch>` while the branch exists, else `git show --stat --format= <merge commit>`, else the paths written by `write_file`/`edit_file` from the trace, flagged as approximate), validations (`ValidationFinished`), last QA verdict. `history::project_history(filter)` over Ready/Done by default, `--all` for Failed/Cancelled too.
- `trace::run_trace(store, task, run) -> Vec<Call>`: pairs `ToolCalled`/`ToolReturned` by `call` (by order and tool name for old logs, marked `paired: "by_order"`), attaches the output file path, groups by subtask and role.
- Optional cost: `[pricing."<provider>/<model>"] input, output, cache_read, cache_write` per million tokens in `config.toml`; `TaskHistory.cost` is `Some` only when every model used has a price. Nothing is estimated silently.

Verification: fixtures of `events.jsonl` (old and new schema), a temp git repo for changed files, unit tests on pairing, ordering and cost.

## Step 3 — CLI (crate vibe-cli)

- `vibe events` with no `REF`: global feed, `--follow`, `--since <RFC3339|duration>`, `--type <name>` (repeatable), `--task <REF>` (repeatable); each line prefixed by `#number`. `--json` prints `TaggedEnvelope`s.
- `vibe history [REF] [--all] [--json]`: table per task (number, title, status, runs, commits, files, tokens, active time, cost when priced, finished date); with `REF`, the full detail (runs, commits with messages, files with status, validations, QA).
- `vibe trace <REF> [--run <id>|--all] [--tool <name>] [--subtask <id>] [--full] [--json]`: one block per call: role, subtask, tool, arguments (complete, pretty JSON), duration, exit code, output (preview by default, `--full` reads the output file), errors highlighted.
- `vibe task show` prints the branch from the record.

## Step 4 — Server and web UI

- Routes: `GET /api/events?since=&type=&task=` and `GET /api/stream?since=&type=&task=&token=` (global SSE, `id` = `at`, data = `TaggedEnvelope`); `GET /api/history?all=` and `GET /api/history/{task}`; `GET /api/tasks/{task}/trace?run=&all=` and `GET /api/tasks/{task}/trace/{call}/output` (text). Existing per-task routes unchanged. The API table in `docs/src/user/cli.md` follows.
- Web UI: views *Tasks* (existing), *Activity* (global feed with type chips and task filter, click selects the task), *History* (table, expandable per task), *Evaluations* (existing); task detail gains a *Trace* tab (calls list, expandable full output loaded on demand). The single `EventSource` per task becomes one global stream feeding both the selected task and the activity view.

## Step 5 — TUI

- Screens: `Tasks` (existing), `Activity` (global, `A`), `History` (`H`); the task detail gains a `Trace` tab with `Enter` to expand a call's output. Event reading switches to the incremental reader.

## Step 7 — macOS app (native UX)

A SwiftUI app for macOS 14+, `apps/macos/VibeFactory/`, generated with `xcodegen` from a `project.yml` like Vincent's other apps (`Templates/AppKitTemplate`), signed and notarised later with the standard `Scripts/release.sh` pipeline (DMG under `release/`). The template is copied by hand (macOS target only: `Views/`, `ViewModels/`, `Services/Keychain.swift`, `Localization/`, `project.yml`, `Scripts/release.sh`, icon generator); its `bootstrap.sh` is not used because it re-initialises git and targets a standalone repository.

- **Connection.** The app is a client of the server API only (ADR-007: one seam). It opens a project folder (recent projects list, drag and drop), starts `vibe serve --project <dir>` as a child process on a free port with a token it reads from the server's stdout / `.vibe/server.token`, and stops it when the window closes; it can also connect to an already running server (URL + token) for the `vibe serve` started in a terminal.
- **Windows and views.** One window per project: sidebar (Tasks board by status, Activity, History, Evaluations), detail with tabs Overview (spec, plan, QA, budget gauges, approval banner with Approve/Reject), Activity (live, `agent_delta` streaming text), Trace (calls with expandable output), Changes. Toolbar: New task, Run/Resume, Cancel, Approve, Reject. Menu bar item with the number of running tasks and pending approvals; user notifications on `approval_requested`, `run_finished`, `paused`.
- **Data layer.** A small Swift package `VibeAPI` (URLSession, `Codable` models generated by hand from `events.md` and the API table, SSE parser for `/api/stream` with reconnection from the last `id`). Unit tests with recorded JSON fixtures taken from a real `.vibe/`.
- **Scope kept out** for the first version: plan editing, settings editor, multi-server. Sparkle auto-update and the DMG layout come with the first tagged release of the app.
- **Verification.** `xcodebuild -scheme VibeFactory -configuration Debug build` and the package tests in CI on `macos-latest` (a new job, does not block the Rust jobs); a manual session against `vibe serve` on this repository.

## Order and size

Steps 1 → 2 → 3 → 4 → 5 → 6 → 7, one commit each on the branch (4 and 5 can run in parallel after 3; 7 needs 4's API). Step 1 is the only one touching the engine; 2–6 are read-only over `.vibe/` and git; 7 is a separate app. Rough size: 1 and 2 are the bulk (two days each), 3–5 a day each, 6 half a day, 7 three to four days.

## Decisions taken in this proposal (say if you disagree)

1. Full tool outputs are stored by default, capped at 100 000 chars per call, under the already-ignored `.vibe/tool-output/`. Disk cost per run ≈ the size of what the model read; `vibe task discard` cleans it.
2. Money cost appears only with a user-supplied `[pricing]` table; tokens and active time are always shown.
3. The TUI gets the three views in a minimal form (lists and one expandable output), the web UI the richer one.
4. Schema stays 2: only optional fields and new event types are added.
